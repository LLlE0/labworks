## 1. Цель работы

Целью лабораторной работы является программирование аппаратной части информационной системы мониторинга безопасности Wi-Fi сетей. В ходе работы необходимо разработать прошивку микроконтроллера ESP8266, обеспечивающую периодическое сканирование радиоэфира и передачу результатов по последовательному интерфейсу; реализовать устойчивый программный приём цифрового сигнала от датчика на стороне сервера; модернизировать пользовательский интерфейс для корректного отображения текущего скана, устранения дублирующихся угроз и оперативного разрешения конфликтов (добавление сети в реестр доверенных). Хранение данных на текущем этапе выполняется в массивах и объектах внутри runtime-кода приложения. Разработка базы данных планируется в рамках следующей лабораторной работы.

## 2. Теоретическая часть

**ESP8266** — микроконтроллер с интегрированным Wi-Fi модулем производства Espressif Systems. Поддерживает стандарты IEEE 802.11 b/g/n, содержит встроенный TCP/IP-стек и может работать в режиме станции (STA) или точки доступа (AP). Для задач мониторинга безопасности ключевой возможностью является пассивное/активное сканирование эфира: микроконтроллер обнаруживает точки доступа в зоне действия и для каждой сети возвращает SSID, BSSID, RSSI и тип шифрования. В данной работе ESP8266 используется как аппаратный цифровой датчик: он не подключается к чужим сетям, а периодически сканирует спектр и выдаёт результат во внешнюю систему.

**Arduino Core for ESP8266 / C++** — среда и язык разработки прошивки. Программа для микроконтроллера строится по классической схеме `setup()` / `loop()`: в `setup()` выполняется однократная инициализация (UART, режим Wi-Fi), в `loop()` — циклический опрос и формирование выходного сигнала. Библиотека `ESP8266WiFi.h` предоставляет API сканирования (`WiFi.scanNetworks`), чтения параметров сети (`WiFi.SSID`, `WiFi.BSSIDstr`, `WiFi.RSSI`, `WiFi.encryptionType`) и очистки результатов (`WiFi.scanDelete`).

**UART / USB Serial** — проводной канал передачи цифрового сигнала от датчика к компьютеру. На стороне платы данные уходят через аппаратный UART; на стороне ПК они появляются как устройство вида `/dev/ttyUSB0` (в стенде использовался преобразователь CH340). Параметры линии: скорость 115200 бод, 8 бит данных, без контроля чётности. Открытие порта с активными сигналами DTR/RTS может удерживать ESP8266 в состоянии сброса, поэтому при приёме эти линии необходимо программно опускать.

**JSON** — текстовый формат обмена данными. Датчик формирует одно JSON-сообщение на каждый цикл сканирования. Сообщение содержит идентификатор устройства (`device_id`) и массив сетей (`networks`) с полями `ssid`, `bssid`, `rssi`, `encryption_type`. Такой формат удобен для потоковой передачи: сервер накапливает байты в буфере и выделяет завершённые объекты по балансу фигурных скобок с учётом строковых литералов.

**Дискретизация сигнала датчика** — выборка состояния радиоэфира с фиксированным периодом. В прошивке задан интервал `SCAN_INTERVAL_MS = 15000` (одна выборка каждые 15 секунд) и задержка первого скана `FIRST_SCAN_DELAY_MS = 2000`, чтобы после старта успела инициализироваться радиочасть. Таким образом, поток данных от аппаратной части является дискретным временным рядом снимков Wi-Fi окружения.

### 2.1 Исходные признаки для классификации угроз

Обнаружение угроз в системе основано не на анализе содержимого трафика, а на **пассивном сопоставлении параметров точек доступа**, полученных от аппаратного датчика, с **реестром доверенных сетей** конкретного здания. Для каждой обнаруженной сети датчик передаёт четыре признака:

| Признак | Смысл | Роль в классификации |
|---|---|---|
| **SSID** | Имя сети (Service Set Identifier) | Сопоставление с «известным» именем доверенной сети; совпадение SSID при другом BSSID — признак атаки Evil Twin |
| **BSSID** | MAC-адрес точки доступа (Basic Service Set Identifier) | Главный идентификатор физической точки; совпадение с доверенным BSSID означает легитимную AP |
| **RSSI** | Уровень сигнала, dBm | В текущей версии не участвует в правилах классификации, сохраняется как измерительный параметр окружения |
| **encryption_type** | Тип защиты (OPEN, WEP, WPA, WPA2, AUTO, UNKNOWN) | Открытое шифрование (`OPEN`) выделяет класс Rogue AP среди сетей вне реестра |

Реестр доверенных сетей задаётся оператором для здания и содержит как минимум тройку `(SSID, BSSID, encryption_type)`. Именно относительно этого реестра каждая точка из скана ESP8266 получает уровень угрозы и, при необходимости, тип угрозы.

Важно различать два уровня результата классификации:

1. **Уровень угрозы (`threat_level`)** — агрегированная оценка для отображения в таблице скана: `SAFE`, `WARNING`, `CRITICAL`.
2. **Тип угрозы (`threat_type`) и критичность (`severity`)** — детализация для журнала угроз: создаётся только если сеть **не** признана безопасной.

### 2.2 Типы угроз, обрабатываемые системой

Ниже подробно описаны все классы, которые система умеет назначать сети. Порядок перечисления совпадает с **приоритетом проверки** в алгоритме: более специфичные и опасные случаи разбираются раньше общих.

#### SAFE — безопасная (легитимная) сеть

**Суть.** Обнаруженная точка доступа полностью соответствует записи в реестре доверенных сетей здания: совпадает **BSSID** (MAC-адрес). Совпадение по BSSID считается достаточным доказательством легитимности, потому что MAC-адрес точки доступа уникально идентифицирует конкретное радиоустройство в рамках модели угроз лабораторной системы.

**Условия обнаружения (теория):**
- в реестре доверенных сетей здания существует запись с тем же BSSID, что у обнаруженной сети;
- при этом SSID и тип шифрования в скане могут незначительно отличаться от реестра (например, временное сокрытие SSID) — приоритет отдаётся идентификации по BSSID.

**Уровень:** `SAFE`. Запись в журнал угроз **не создаётся**.

**Интерпретация для оператора.** Сеть считается ожидаемой инфраструктурой здания. Дополнительных действий не требуется. Если оператор ошибочно добавил в доверенные чужой BSSID, система будет помечать его как SAFE — ответственность за корректность реестра лежит на администраторе.

#### EVIL_TWIN — атака «злой близнец» (CRITICAL)

**Суть.** Классическая атака на Wi-Fi: злоумышленник поднимает точку доступа с **тем же SSID**, что у легитимной сети организации, но с **другим BSSID**. Пользователи видят привычное имя сети и могут подключиться к поддельной AP; далее возможны перехват трафика, фишинг captive-portal, атака «человек посередине».

**Условия обнаружения (теория):**
1. BSSID обнаруженной сети **отсутствует** в реестре доверенных (иначе сработал бы класс SAFE);
2. SSID обнаруженной сети **совпадает** с SSID хотя бы одной доверенной сети того же здания;
3. следовательно, имя «знакомое», а физическая точка — «чужая».

**Уровень:** `CRITICAL`. Тип угрозы: `EVIL_TWIN`. Критичность записи: `CRITICAL`.

**Почему это самый высокий приоритет среди угроз.** Совпадение SSID с корпоративной/доверенной сетью означает прямой риск для пользователей, которые ориентируются на имя сети. Даже если поддельная точка использует шифрование (WPA2 и т.п.), для системы это всё равно EVIL_TWIN: наличие шифрования не отменяет факт подмены идентификатора сети.

**Пример.** В реестре есть `SSID=SFEDU-SAFE`, `BSSID=AA:BB:CC:DD:EE:01`. Датчик видит `SSID=SFEDU-SAFE`, `BSSID=AA:BB:CC:DD:EE:04`. Результат — `CRITICAL` / `EVIL_TWIN`.

#### ROGUE_AP — несанкционированная открытая точка доступа (WARNING / MEDIUM)

**Суть.** Rogue AP — точка доступа, развёрнутая в зоне мониторинга без ведома администратора. В лабораторной модели наиболее однозначным техническим маркером «опасной самодеятельности» считается **открытое шифрование** (`OPEN`): к такой сети может подключиться любой клиент без пароля, что создаёт риск утечки данных и площадку для атак на клиентов.

**Условия обнаружения (теория):**
1. сеть не попала в SAFE (BSSID неизвестен реестру);
2. сеть не попала в EVIL_TWIN (SSID не совпадает ни с одной доверенной);
3. `encryption_type` после нормализации равен `OPEN`.

**Уровень:** `WARNING`. Тип угрозы: `ROGUE_AP`. Критичность записи: `MEDIUM`.

**Интерпретация.** Это не обязательно атака: иногда открытыми бывают гостевые сети, принтеры, IoT. Но с точки зрения политики безопасности здания открытая неизвестная AP требует внимания администратора — либо внести в доверенные (если легитимна), либо физически найти и отключить.

**Отличие от EVIL_TWIN.** Rogue AP в данной системе — это «незнакомое имя + OPEN». Если у открытой сети имя совпало с доверенным SSID, сработает EVIL_TWIN (более опасный класс), а не ROGUE_AP.

#### UNKNOWN_DEVICE — неизвестное зашифрованное устройство (WARNING / LOW)

**Суть.** Зашифрованная сеть, которой нет в реестре доверенных и чьё имя не совпадает с доверенными SSID. Это самый массовый класс в реальном эфире города/кампуса: соседские роутеры, телефоны в режиме модема, чужие офисы в радиусе ESP8266.

**Условия обнаружения (теория):**
1. BSSID неизвестен реестру;
2. SSID не совпадает с доверенными;
3. шифрование **не** `OPEN` (WEP / WPA / WPA2 / AUTO / UNKNOWN и т.д.).

**Уровень:** `WARNING`. Тип угрозы: `UNKNOWN_DEVICE`. Критичность записи: `LOW`.

**Интерпретация.** Сам по себе класс не означает атаки: это сигнал «устройство вне политики учёта». Оператор может:
- добавить сеть в доверенные (кнопка «Доверенная»), если она легитимна для здания;
- оставить как активную угрозу низкой критичности для дальнейшего наблюдения;
- игнорировать соседские сети, если зона покрытия датчика шире периметра здания (ограничение пассивного Wi-Fi мониторинга).

**Почему критичность LOW.** Неизвестная зашифрованная сеть реже является целенаправленной атакой на пользователей здания, чем Evil Twin или открытый Rogue AP. Тем не менее без учёта таких сетей реестр доверенных теряет смысл как «белый список» инфраструктуры.

### 2.3 Приоритет правил и модель принятия решения

Алгоритм классификации — **дерево решений с ранним выходом** (первое сработавшее правило определяет результат):

```
вход: (ssid, bssid, encryption_type), реестр доверенных здания
  │
  ├─1─ BSSID ∈ доверенные ──────────────────────────► SAFE
  │                                                   (угроза не создаётся)
  │
  ├─2─ SSID ∈ доверенные (BSSID ∉ доверенные) ───────► CRITICAL / EVIL_TWIN
  │
  ├─3─ encryption_type == OPEN ─────────────────────► WARNING / ROGUE_AP
  │
  └─4─ иначе ───────────────────────────────────────► WARNING / UNKNOWN_DEVICE
```

Такой порядок гарантирует:
- легитимная точка не будет ошибочно помечена как угроза;
- подмена SSID (Evil Twin) не «маскируется» под обычный UNKNOWN_DEVICE даже при наличии WPA2;
- открытые сети выделяются из общей массы неизвестных раньше, чем сработает общее правило UNKNOWN_DEVICE.

Без механизмов дедупликации при периодическом сканировании (15 с) одна и та же точка доступа порождала бы новую запись об угрозе на каждом цикле. Поэтому в ЛР3 дополнительно введены правила: актуальный снимок эфира затирает предыдущий список точек; активная угроза уникальна по паре «здание + BSSID».

### 3.1 Разработка прошивки ESP8266

Прошивка размещена в файле `firmware/esp8266_wifi_scanner.ino` и написана на C++ с использованием Arduino Core for ESP8266.

**Идентификация устройства.** Константа `DEVICE_ID = "ESP8266-DEMO-001"` включается в каждое JSON-сообщение. Серверная часть сопоставляет этот идентификатор с зарегистрированным датчиком и отклоняет данные от неизвестных устройств.

**Инициализация (`setup`).** При старте открывается последовательный порт на 115200 бод, отключается отладочный вывод Wi-Fi в UART (`Serial.setDebugOutput(false)`), чтобы служебные сообщения не портили JSON-поток. Радиомодуль переводится в режим станции (`WIFI_STA`), вызывается `WiFi.disconnect()`, отключается сохранение Wi-Fi-настроек во flash (`WiFi.persistent(false)`). Датчик не ассоциируется с какой-либо сетью — он только сканирует.

**Цикл работы (`loop`).** Используется неблокирующая схема на базе `millis()`: пока не наступило время `nextScanAt`, выполняется короткий `delay(20)` и выход из итерации. По наступлении момента вызывается `scanAndPrint()`, после чего планируется следующий скан через 15 секунд. Такой подход задаёт частоту дискретизации аппаратного сигнала и не блокирует микроконтроллер на длинных `delay(15000)`.

**Сканирование.** Функция `WiFi.scanNetworks(false, true)` выполняет синхронный скан с показом скрытых сетей (`show_hidden = true`). При ошибке (`networkCount < 0`) в UART отправляется валидный JSON с пустым массивом `networks`, чтобы приёмник не зависал в ожидании. После формирования ответа вызывается `WiFi.scanDelete()` для освобождения памяти.

**Формирование JSON.** Функция `buildScanJson` собирает строку вида:

```json
{
  "device_id": "ESP8266-DEMO-001",
  "networks": [
    {
      "ssid": "Campus-WiFi",
      "bssid": "AA:BB:CC:DD:EE:01",
      "rssi": -54,
      "encryption_type": "WPA2"
    }
  ]
}
```

Для корректной сериализации имён сетей реализована `appendJsonString`: экранируются кавычки, обратный слэш и управляющие символы, чтобы SSID с пробелами или спецсимволами не ломали разбор на стороне ПК. Тип шифрования из числовых констант SDK (`ENC_TYPE_CCMP`, `ENC_TYPE_NONE` и др.) преобразуется в человекочитаемые значения `WPA2`, `OPEN`, `WEP`, `WPA`, `AUTO`, `UNKNOWN`.

**Загрузка на плату.** Исходник компилируется и прошивается через Arduino IDE / PlatformIO с выбранной платой NodeMCU / Generic ESP8266. После подключения по USB на хосте появляется порт (например, `/dev/ttyUSB0`). Пользователь должен иметь права доступа к группе `dialout`. Готовность датчика проверяется появлением периодических JSON-строк в мониторе порта или в логе шлюза приёма.

Таким образом, аппаратная часть формирует дискретный цифровой сигнал — поток JSON-сообщений с периодом 15 с — полностью готовый к проводной передаче в серверную часть ИС.

### 3.2 Приём данных с аппаратного датчика

Приём реализован отдельным процессом `serial_gateway.py`. Он связывает UART-датчик с HTTP API приложения и решает задачи буферизации, восстановления границ сообщений и устойчивости к обрывам связи.

**Ожидание сервера.** Перед открытием порта шлюз опрашивает доступность веб-приложения. Пока сервер не поднят, повторные попытки выполняются с паузой 2 с — это исключает потерю первых сканов при параллельном запуске компонентов.

**Конфигурация порта.** Имя устройства (`/dev/ttyUSB0`) и скорость (115200) читаются из API настроек (`GET /api/serial-config`) либо из переменных окружения. Параметры периодически обновляются (каждые 3 с): при смене порта или baudrate соединение переоткрывается без перезапуска процесса. Это позволяет менять TTY из веб-раздела «Serial».

**Открытие UART и сигналы управления.** Порт открывается библиотекой `pyserial` с таймаутом чтения 0,5 с. Для плат с CH340 принудительно выставляются `dtr = False` и `rts = False`, иначе ESP8266 может оставаться в reset и не передавать данные. После короткой паузы входной буфер очищается.

**Буферизация и выделение JSON.** Поток читается чанками до 1024 байт и накапливается в строковом буфере. Функция `extract_json_objects` проходит буфер посимвольно, отслеживает глубину вложенности `{` / `}` и игнорирует скобки внутри строковых литералов (с учётом экранирования `\`). При достижении нулевой глубины извлекается ровно один завершённый объект, остаток буфера сохраняется для следующих чанков. Если буфер превышает 64 КБ, выполняетсяется «мусор» до первой `{` — защита от рассинхронизации потока.

**Валидация и пересылка.** Извлечённая строка разбирается `json.loads`. Сообщение принимается только при наличии полей `device_id` и `networks`. Далее выполняется `POST /api/scan` с телом JSON. В журнал шлюза пишется ответ сервера (число сетей, число новых/обновлённых угроз), что упрощает отладку аппаратного канала.

**Обработка на стороне приложения.** Эндпоинт `/api/scan` принимает payload от шлюза, сопоставляет `device_id` с зарегистрированным датчиком и для каждой сети выполняет классификацию (см. п. 3.3). Результаты текущего скана замещают предыдущий снимок эфира для данного устройства: список точек доступа на главной странице всегда соответствует последней выборке датчика. История угроз при этом не уничтожается — меняется только актуальное представление радиообстановки.

Цепочка передачи данных в ЛР3:

```
ESP8266 (скан 15 с)
    → UART/USB JSON
    → serial_gateway (буфер + разбор)
    → POST /api/scan
    → analyze_network / учёт угроз
    → веб-интерфейс
```

### 3.3 Реализация обнаружения и классификации угроз

После приёма JSON от датчика каждая сеть из массива `networks` проходит этап предварительной обработки — функцию `analyze_network(building_id, ssid, bssid, encryption_type)`. Здание определяется по привязке зарегистрированного ESP-устройства (`device_id` → здание). Таким образом, один и тот же BSSID в разных зданиях классифицируется независимо, относительно своего реестра доверенных сетей.

#### Подготовка признаков

Перед сравнением выполняется нормализация:
- `bssid` приводится к верхнему регистру и обрезаются пробелы (`normalize_bssid`) — чтобы `aa:bb:...` и `AA:BB:...` считались одним адресом;
- пустой SSID от датчика (скрытая сеть) заменяется на литерал `"<hidden>"`;
- `encryption_type` при проверке на открытую сеть сравнивается без учёта регистра (`encryption_type.upper() == "OPEN"`).

Функция возвращает пару `(threat_level, threat_data)`:
- для SAFE: `("SAFE", None)` — угроза не создаётся;
- для остальных: `("CRITICAL"|"WARNING", (threat_type, severity))`.

#### Реализация правила SAFE

В массиве доверенных сетей здания выполняется поиск записи с тем же `bssid`. При первом совпадении алгоритм немедленно возвращает `SAFE` и `None`. Поиск по SSID на этом шаге **не выполняется**: идентификация легитимной точки идёт строго по MAC-адресу AP. Это соответствует теоретической модели (п. 2.2): поддельная сеть с чужим BSSID не может «пройти» как SAFE, даже если злоумышленник скопировал SSID.

#### Реализация правила EVIL_TWIN

Если SAFE не сработал, выполняется поиск доверенной записи с тем же `ssid`. Условие истинно только когда:
- имя сети уже известно политике здания;
- но BSSID другой (иначе сработал бы предыдущий шаг).

Тогда возвращается `("CRITICAL", ("EVIL_TWIN", "CRITICAL"))`. В журнале угроз создаётся (или обновляется — см. дедупликацию) запись с типом `EVIL_TWIN` и максимальной критичностью. В таблице текущего скана сеть помечается бейджем `CRITICAL`.

Практический смысл: прошивка ESP лишь измеряет эфир; решение «это подмена корпоративного SSID» принимает серверная логика по реестру. Датчик не обязан знать список доверенных сетей — он поставляет сырые признаки.

#### Реализация правила ROGUE_AP

Если ни BSSID, ни SSID не найдены в доверенных, проверяется открытость сети:

```python
if encryption_type.upper() == "OPEN":
    return "WARNING", ("ROGUE_AP", "MEDIUM")
```

Значение `OPEN` на стороне прошивки формируется из константы SDK `ENC_TYPE_NONE` функцией `encryptionName()`. Таким образом цепочка обнаружения Rogue AP сквозная:

```
ESP8266: encryptionType == ENC_TYPE_NONE
    → JSON: "encryption_type": "OPEN"
    → analyze_network: ROGUE_AP / MEDIUM
```

Сеть получает уровень `WARNING` (не CRITICAL), так как неизвестная открытая AP опасна, но не является прямой подменой уже учтённого имени сети.

#### Реализация правила UNKNOWN_DEVICE

Любой оставшийся случай — неизвестный BSSID, неизвестный SSID, шифрование не OPEN — классифицируется как:

```python
return "WARNING", ("UNKNOWN_DEVICE", "LOW")
```

Это правило-«хвост» дерева решений: оно гарантирует, что ни одна сеть вне реестра не останется без оценки. На практике при работе реального ESP8266 в городской среде именно `UNKNOWN_DEVICE` составляет основную массу активных угроз до тех пор, пока оператор не сузит реестр доверенных или не пометит нужные сети кнопкой «Доверенная».

#### Сводка соответствия «теория → код → UI»

| Класс | Условие в коде | `threat_level` | `threat_type` | `severity` | Запись угрозы | Бейдж в UI |
|---|---|---|---|---|---|---|
| SAFE | `TrustedNetwork` по `bssid` найдена | SAFE | — | — | нет | SAFE (зелёный) |
| EVIL_TWIN | доверенный `ssid`, чужой `bssid` | CRITICAL | EVIL_TWIN | CRITICAL | да | CRITICAL (красный) |
| ROGUE_AP | вне реестра и `encryption == OPEN` | WARNING | ROGUE_AP | MEDIUM | да | WARNING (жёлтый) |
| UNKNOWN_DEVICE | вне реестра и не OPEN | WARNING | UNKNOWN_DEVICE | LOW | да | WARNING (жёлтый) |

#### Создание и сопровождение записи об угрозе

Если `threat_data` не пуст, вызывается `upsert_threat(...)`:
- ищется активная угроза с тем же `building_id` и `bssid` (статус ≠ `resolved`);
- если найдена — обновляются SSID, тип, критичность и время изменения (**дубль не создаётся**);
- если не найдена — создаётся новая запись со статусом `new`.

Если сеть классифицирована как SAFE (в том числе после того, как оператор добавил её в доверенные), вызывается `resolve_threats_for_network`: все активные угрозы по этому BSSID получают статус `resolved`. История сохраняется в журнале, но счётчик «Активные угрозы» на главной больше их не учитывает.

#### Жизненный цикл угрозы в системе

```
скан ESP → analyze_network
              │
              ├─ SAFE ──────────────► закрыть активные угрозы по BSSID (если были)
              │
              └─ EVIL_TWIN /
                 ROGUE_AP /
                 UNKNOWN_DEVICE ───► upsert_threat
                                        ├─ новая запись (status=new)
                                        └─ или обновление существующей
              │
              ▼
оператор нажимает «Доверенная»
              │
              ├─ сеть в реестр доверенных
              └─ resolve → status=resolved
              │
              ▼
следующий скан той же AP → SAFE (угроза больше не поднимается)
```

Статусы записи об угрозе, доступные в разделе «Угрозы»: `new`, `confirmed`, `resolved`. Для метрики активных угроз на дашборде учитываются все записи, у которых статус **не** `resolved`.

### 3.4 Модернизация интерфейса: устранение дублей и разрешение конфликтов

После подключения реальной аппаратной части обнаружилась проблема накопления ложных «активных угроз»: при периоде сканирования 15 с одна и та же неизвестная точка доступа регистрировалась как новая угроза на каждом цикле. Интерфейс быстро становился нечитаемым (сотни и тысячи записей при неизменном эфире). В рамках ЛР3 выполнена модернизация логики отображения и разрешения конфликтов.

**Текущий снимок вместо «ленты» всех сканов.** На главной странице таблица «Точки текущего скана» показывает только сети последней успешной выборки датчика. В подзаголовке выводится метка времени скана. Предыдущий список точек для устройства затирается при поступлении нового сообщения. Это соответствует физической природе датчика: оператору важен актуальный срез эфира, а не накопление всех прошлых SSID в одной таблице.

**Дедупликация угроз.** Активная угроза уникальна в пределах пары «здание + BSSID». При повторном обнаружении той же точки существующая запись обновляется (тип, критичность, SSID, привязка к свежему результату скана), новая копия не создаётся. Если сеть стала доверенной / безопасной, открытая угроза по этому BSSID переводится в статус `resolved`. Полный журнал угроз (в том числе закрытые) сохраняется для последующего разбора; в счётчике «Активные угрозы» учитываются только неразрешённые записи.

**Разрешение конфликтов из UI.** На дашборде у каждой небезопасной точки и у каждой активной угрозы добавлена кнопка «Доверенная». По нажатию сеть заносится в реестр доверенных (SSID, BSSID, тип шифрования, здание), связанные активные угрозы закрываются. При следующем скане датчика эта точка классифицируется как SAFE и больше не поднимает предупреждение. Таким образом оператор прямо из главного экрана снимает конфликт «неизвестное устройство / потенциальная угроза» без перехода в отдельный раздел настройки.

**Отображение.** Для угроз в интерфейсе показываются тип (`UNKNOWN_DEVICE`, `ROGUE_AP`, `EVIL_TWIN`), критичность, SSID и BSSID. Статусы сетей в таблице скана подсвечиваются бейджами `SAFE` / `WARNING` / `CRITICAL`. Внешний вид главной страницы после модернизации представлен на рисунке 1.


В результате модернизации интерфейс отражает реальную работу аппаратного датчика: список точек соответствует последнему скану, угрозы не размножаются на каждом цикле дискретизации, а конфликтные сети оперативно переводятся в доверенные.

```python
def extract_json_objects(buffer):
    objects = []
    start = None
    depth = 0
    in_string = False
    escaped = False

    for index, char in enumerate(buffer):
        if start is None:
            if char == "{":
                start = index
                depth = 1
            continue
        # ... учёт строк и экранирования ...
        if char == "{":
            depth += 1
        elif char == "}":
            depth -= 1
            if depth == 0:
                objects.append(buffer[start:index + 1])
                return objects, buffer[index + 1:]

    return objects, buffer[start:] if start is not None else ""
```

### app.py (фрагмент — классификация угроз)

```python
def analyze_network(building_id, ssid, bssid, encryption_type):
    bssid = normalize_bssid(bssid)

    # 1) SAFE — MAC точки есть в реестре доверенных
    trusted_bssid = TrustedNetwork.query.filter_by(
        building_id=building_id, bssid=bssid
    ).first()
    if trusted_bssid:
        return "SAFE", None

    # 2) EVIL_TWIN — знакомый SSID, чужой BSSID
    trusted_ssid = TrustedNetwork.query.filter_by(
        building_id=building_id, ssid=ssid
    ).first()
    if trusted_ssid:
        return "CRITICAL", ("EVIL_TWIN", "CRITICAL")

    # 3) ROGUE_AP — неизвестная открытая сеть
    if encryption_type.upper() == "OPEN":
        return "WARNING", ("ROGUE_AP", "MEDIUM")

    # 4) UNKNOWN_DEVICE — неизвестная зашифрованная сеть
    return "WARNING", ("UNKNOWN_DEVICE", "LOW")
```
